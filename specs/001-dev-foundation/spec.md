# Feature Specification: 開発基盤の整備（現行サイト調査・デザイン基盤・画面テスト・README自動更新）

**Feature Branch**: `001-dev-foundation`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "現行サイト(https://waku-8.com/)のページ構成とデザイン(配色・フォント・余白)を調査し、デザイントークン・共通レイアウト(ヘッダー/フッター/ナビ)・スタイルガイドページ・Playwrightによる画面テスト環境とGitHub Actionsでの自動実行を整備する。あわせて、developへのpush時にspecs配下の仕様・タスクからREADMEの進捗表・仕様一覧を自動生成して更新する仕組みを作る"

## User Scenarios & Testing *(mandatory)*

本機能の利用者は、主に次の2者である。

- **開発者**：新サイトを制作・保守する人（現時点ではリポジトリの所有者）
- **店舗関係者**：和久屋の店主・スタッフなど、制作の進み具合や仕様を確認する人

本機能はお客様向けのページを完成させるものではなく、以降のページ制作（002以降の機能）を
開発原則（constitution v1.0.0）に沿って進めるための土台を作る。

### User Story 1 - 現行サイトの構成とデザインを記録する (Priority: P1)

開発者は、現行サイト https://waku-8.com/ のすべてのページについて、ページの一覧・階層・
ナビゲーションの構成と、配色・フォント・文字サイズ・余白などのデザインの特徴を調べ、
リポジトリ内の資料として残す。あわせて、各ページの現時点の見た目（スマートフォン幅とPC幅）を
記録しておく。以降の機能では、この資料を見れば「何を踏襲すべきか」が分かる。

**Why this priority**: 開発原則I（既存サイトの踏襲）を守るには、踏襲する対象が記録されている
必要がある。現行サイトは新サイト公開時に置き換わるため、早い段階で記録しないと失われる。
ほかのすべてのストーリーの前提になる。

**Independent Test**: 資料だけを見て、現行サイトのページ一覧・各ページのURL・ナビゲーションの
並び順・主要な色とフォントを、現行サイトを開かずに説明できることを確認する。

**Acceptance Scenarios**:

1. **Given** 現行サイトが公開されている, **When** 開発者が調査資料を作成する, **Then** 現行サイトの
   ナビゲーションやリンクからたどれるすべてのページが、URL・ページ名・親子関係とともに一覧になっている
2. **Given** 調査資料がある, **When** 開発者が新サイトのURL設計を始める, **Then** 現行URLごとに
   「新サイトでの対応先（未定可）」を書き込める旧URL対応表の素案がある
3. **Given** 調査資料がある, **When** 開発者がデザインの値を確認する, **Then** 主要な色・フォント・
   文字サイズ・余白・角丸などが、具体的な値と使われている場所とともに記録されている
4. **Given** 調査資料がある, **When** 現行サイトが閉鎖・変更された後に見返す, **Then** 各ページの
   スマートフォン幅とPC幅の見た目を、保存した画像で確認できる

---

### User Story 2 - デザイントークン・共通レイアウト・スタイルガイドを用意する (Priority: P1)

開発者は、調査結果をもとにデザインの値をデザイントークンとして1か所にまとめ、ヘッダー・フッター・
ナビゲーションからなる全ページ共通のレイアウトを作る。作った部品はスタイルガイドページで一覧でき、
店舗関係者もそのページを見て、現行サイトの印象が保たれているかを確認できる。

**Why this priority**: 開発原則VI・VIIにより、ページ制作は共通レイアウトとトークンを使うことが
前提になる。これがないと002以降のページ制作に着手できない。

**Independent Test**: 開発環境でスタイルガイドページを開き、トークン（色・フォント・余白など）と
共通部品が一覧表示され、共通レイアウトを適用したサンプルページがスマートフォン幅とPC幅で
崩れずに表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** デザイントークンが定義されている, **When** トークンの色の値を1か所で変更する,
   **Then** 共通レイアウトとスタイルガイド上のすべての該当箇所に変更が反映される
2. **Given** 共通レイアウトがある, **When** サンプルページを画面幅360pxで表示する, **Then** 横スクロールが
   発生せず、ナビゲーションのすべての項目にたどり着ける
3. **Given** 共通レイアウトがある, **When** サンプルページをPC幅で表示する, **Then** ヘッダー・ナビ・
   フッターの構成と並び順が現行サイトの調査結果と一致している（変更した箇所は理由が記録されている）
4. **Given** スタイルガイドページがある, **When** 本番用にサイトを出力する, **Then** スタイルガイド
   ページは公開対象に含まれない
5. **Given** 共通レイアウトがある, **When** ナビゲーションからカラーミーショップへのリンクを選ぶ,
   **Then** https://waku-8.shop-pro.jp/ に移動する

### User Story 3 - 画面の自動テストをpushのたびに実行する (Priority: P2)

開発者がコードをpushするかpull requestを作ると、自動でテストが実行され、スマートフォン幅とPC幅の
スクリーンショットの比較、アクセシビリティのチェック、リンク切れと主要な導線の確認、
メタ情報・構造化データ・サイトマップの確認が行われる。失敗した場合は、どの画面のどこが
問題なのかが結果から分かる。

**Why this priority**: 開発原則VII・VIIIで必須とされているが、確認対象となる画面（US2）が
先にないと価値が出ないためP2とする。

**Independent Test**: サンプルページの色や余白を意図的に変更してpushし、自動テストが失敗して
差分画像で変更箇所が示されることを確認する。元に戻してpushすると成功することも確認する。

**Acceptance Scenarios**:

1. **Given** 自動テストが設定されている, **When** 開発者が任意のブランチにpushする, **Then** テストが
   自動で実行され、結果（成功・失敗）がリポジトリ上で確認できる
2. **Given** 基準画像がある, **When** 画面の見た目が変わる変更をpushする, **Then** スクリーンショット
   比較が失敗し、基準画像・新しい画像・差分画像を確認できる
3. **Given** 見た目の変更が意図したものである, **When** 開発者が基準画像の更新を指示する,
   **Then** 決まった実行環境で基準画像が作り直され、差分を確認したうえでコミットできる
4. **Given** 自動テストが設定されている, **When** 代替テキストのない画像やコントラスト不足の文字を
   追加する, **Then** アクセシビリティチェックが失敗し、該当箇所が示される
5. **Given** 自動テストが設定されている, **When** 存在しないページへのリンクを追加する,
   **Then** リンクチェックが失敗し、リンク元とリンク先が示される
6. **Given** 自動テストが設定されている, **When** title・meta description・canonical・OGP・構造化データの
   いずれかが欠けたページを追加する, **Then** テストが失敗し、欠けている項目が示される
7. **Given** テストが失敗している, **When** developまたはmainへのマージを試みる, **Then** マージできない
   （またはマージ前に失敗が明示される）

### User Story 4 - READMEを進捗表・仕様書として自動更新する (Priority: P3)

developブランチ（およびmainブランチ）にpushされると、specs配下の各機能の仕様・計画・作業項目から
READMEの自動生成部分が作り直される。開発中、店舗関係者や開発者はREADMEを見るだけで、
どの機能がどの工程まで進み、残りの作業が何かを把握できる。すべての作業が完了した機能は、
進捗ではなく「何ができるサイトなのか」を説明する仕様の一覧としてREADMEに載る。

**Why this priority**: 進捗の見える化は便利だが、サイトの品質や制作そのものには直接影響しないため
P3とする。US1〜US3がなくても単独で動作する。

**Independent Test**: specs配下の作業項目のチェックを1つ完了にしてdevelopにpushし、数分以内に
READMEの完了率と未完了の作業一覧が更新されることを確認する。

**Acceptance Scenarios**:

1. **Given** READMEに自動生成部分の範囲が示されている, **When** developにpushする, **Then** 自動生成部分
   だけが作り直され、範囲外の手書き部分は変更されない
2. **Given** 作業中の機能がある, **When** READMEを見る, **Then** 機能ごとに、現在の工程（仕様・計画・
   作業分解・実装中・完了）、作業項目の完了数と全体数、未完了の作業項目が表示されている
3. **Given** すべての作業項目が完了した機能がある, **When** READMEを見る, **Then** その機能は進捗表ではなく
   仕様一覧の側に、概要とユーザーストーリーの要約とともに表示されている
4. **Given** pushされた変更でREADMEの内容が変わらない, **When** 自動更新が実行される, **Then** 新しい
   コミットは作られない
5. **Given** 自動更新によってREADMEのコミットが作られた, **When** そのコミットがpushされる,
   **Then** 自動更新が再び連鎖して実行され続けることはない
6. **Given** 作業項目ファイルがまだない機能（仕様だけの状態）がある, **When** 自動更新が実行される,
   **Then** その機能は「仕様作成中」などの工程として表示され、処理は失敗しない

---

### Edge Cases

- 現行サイトの一部ページが表示できない・リンク切れになっている場合は、調査資料にその旨を記録し、
  調査全体は止めない。
- 現行サイトで文字が画像として表示されている場合は、その文字の内容も資料に書き起こす
  （開発原則VIII：画像の中の文字だけで情報を伝えない）。
- 現行サイトの色やフォントが、ページによって微妙に異なる場合は、使用頻度の高い値を代表値として
  トークン化し、外れ値は資料に記録したうえで統一するかどうかを判断できるようにする。
- 現行サイトのフォントが、新サイトで利用できない（ライセンス上・技術上の理由）場合は、近い印象の
  代替フォントを候補として記録する。
- アニメーション・日時表示・外部の埋め込み（地図・SNS）など、毎回見た目が変わる部分があると
  スクリーンショット比較が不安定になるため、それらは比較の対象外にするか固定した状態で撮影する。
- 外部サイト（カラーミーショップ・SNSなど）へのリンクは、外部側の一時的な障害でテストが
  失敗しないよう、内部リンクとは扱いを分ける。
- 開発者のPCと自動テスト環境でスクリーンショットが異なる場合は、自動テスト環境の画像を正とする。
- 自動更新のコミットと開発者のpushが同時期に重なった場合でも、どちらかの変更が失われてはならない。
- READMEの自動生成部分の目印が削除・破損している場合は、自動更新は手書き部分を上書きせずに
  失敗し、原因を示す。
- 作業項目ファイルの書式が想定と異なる行（チェック欄のない行など）は、集計の対象外として無視する。

## Requirements *(mandatory)*

### Functional Requirements

**現行サイトの調査（US1）**

- **FR-001**: 現行サイトのナビゲーション・リンク・サイトマップ（存在する場合）からたどれるすべての
  ページについて、URL・ページ名・階層・ナビゲーション上の位置を一覧にした資料を作成しなければならない
- **FR-002**: 現行URLごとに新サイトでの対応先を記入できる、旧URL対応表の素案を作成しなければならない
- **FR-003**: 現行サイトの配色・フォント・文字サイズ・行間・余白・角丸・影などのデザインの値を、
  使用箇所とともに記録しなければならない
- **FR-004**: 現行サイトの全ページについて、スマートフォン幅とPC幅の画面全体の画像を保存しなければならない
- **FR-005**: 現行サイトのロゴ・写真など、新サイトで再利用する可能性のある素材の一覧を作成しなければ
  ならない（利用権限の確認状況を記入できる欄を含む）

**デザイン基盤（US2）**

- **FR-006**: 色・フォント・文字サイズ・余白・角丸・ブレークポイントなどのデザインの値を、
  デザイントークンとして1か所で定義しなければならない
- **FR-007**: ヘッダー・ナビゲーション・フッターからなる共通レイアウトを、全ページで1か所の定義を
  共有する形で提供しなければならない
- **FR-008**: 共通レイアウトは、画面幅360pxから一般的なPC幅まで、横スクロールなしで表示・操作
  できなければならない
- **FR-009**: 共通レイアウトのナビゲーションには、カラーミーショップ（https://waku-8.shop-pro.jp/ ）への
  導線を含めなければならない
- **FR-010**: デザイントークンと共通部品を一覧表示するスタイルガイドページを提供しなければならない。
  スタイルガイドページは本番の公開対象に含めてはならない
- **FR-011**: 共通レイアウトを適用し、テストの対象となるサンプルページを用意しなければならない
- **FR-012**: 共通レイアウトは、JavaScriptが無効な状態でもナビゲーションのすべての項目にたどり着けなければ
  ならない
- **FR-013**: 共通レイアウトは、すべてのページで title・meta description・canonical・OGP・構造化データを
  ページごとに設定できる仕組みを備えなければならない。店舗情報の構造化データの雛形を含める

**画面テストと自動実行（US3）**

- **FR-014**: 全ページについて、スマートフォン幅とPC幅のスクリーンショットを基準画像と比較する
  自動テストを提供しなければならない
- **FR-015**: スクリーンショット比較は、対応ブラウザのエンジン（Chromium系とWebKit系）で実行しなければ
  ならない
- **FR-016**: 全ページについて、アクセシビリティの自動チェックを提供しなければならない
- **FR-017**: 全ページについて、内部リンクの切れと、カラーミーショップへの導線の存在を確認する
  自動テストを提供しなければならない
- **FR-018**: 全ページについて、title・meta description・canonical・OGPの有無と、構造化データの
  書式の正しさ、サイトマップへの掲載を確認する自動テストを提供しなければならない
- **FR-019**: 自動テストは、すべてのブランチへのpushとpull requestのたびに自動で実行されなければならない
- **FR-020**: テストが失敗した場合、失敗したページ・項目と、スクリーンショット比較では基準・実際・差分の
  画像を、結果から確認できなければならない
- **FR-021**: 基準画像は決まった実行環境で作成・更新しなければならず、開発者がその更新を指示できる手段を
  提供しなければならない
- **FR-022**: 自動テストが失敗している変更が、developおよびmainにマージされることを防ぐ設定、または
  その手順を用意しなければならない
- **FR-023**: 開発者が自分のPCでも同じテストを実行できる手順を提供しなければならない
  （スクリーンショット比較の結果は参考扱いとする）

**READMEの自動更新（US4）**

- **FR-024**: READMEは、手書き部分と、目印で範囲を示した自動生成部分に分けなければならない
- **FR-025**: developまたはmainへのpush時に、specs配下の各機能の仕様・計画・作業項目から自動生成部分を
  作り直さなければならない
- **FR-026**: 自動生成部分には、機能ごとの「現在の工程」「作業項目の完了数・全体数・完了率」
  「未完了の作業項目」「仕様へのリンク」を表示しなければならない
- **FR-027**: すべての作業項目が完了した機能は、仕様一覧として「概要」「ユーザーストーリーの要約」
  「仕様へのリンク」を表示しなければならない
- **FR-028**: 自動生成部分には、開発原則のバージョンと最終更新日を表示しなければならない
- **FR-029**: 自動生成の結果に変更がない場合は、コミットを作ってはならない
- **FR-030**: 自動更新によるコミットが、自動更新や自動テストの不要な再実行を連鎖的に引き起こしては
  ならない
- **FR-031**: 自動生成部分の目印が見つからない場合は、READMEを変更せずに失敗し、原因を示さなければ
  ならない
- **FR-032**: 開発者が自分のPCでも同じ自動生成を実行し、結果を確認できなければならない
- **FR-033**: 同じ入力からは常に同じ自動生成結果にならなければならない（実行日時などで内容が
  変わらない）

### Key Entities

- **現行ページ**：現行サイトの1ページ。URL・ページ名・親ページ・ナビゲーション上の位置・
  保存した画像・特記事項（表示できない、画像内の文字がある等）を持つ。
- **旧URL対応**：現行ページのURLと、新サイトでの対応先URL（未定可）、対応方法（同じURL・
  リダイレクト・廃止）の組。
- **デザイントークン**：色・フォント・余白などの名前付きの値。値・用途・現行サイトでの出典を持つ。
- **共通部品**：ヘッダー・ナビゲーション・フッター・ボタンなど、複数ページで使う画面の部品。
  スタイルガイドに表示される。
- **基準画像**：ページ・画面幅・ブラウザエンジンの組ごとに保存する、比較の基準となる画面の画像。
- **機能（Feature）**：specs配下の1ディレクトリ。番号・名前・仕様・計画・作業項目を持ち、
  そこから現在の工程と完了率が決まる。
- **作業項目**：作業項目ファイル内の1つのチェック項目。完了・未完了の状態と、所属するフェーズ
  （またはユーザーストーリー）を持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 現行サイトのナビゲーションからたどれるページの100%が、調査資料の一覧と画像に含まれている
- **SC-002**: 調査資料とスタイルガイドページを見た店舗関係者が、新サイトの共通レイアウトを
  「和久屋のサイトだと分かる」と判断できる
- **SC-003**: デザインの値（色など）を1か所変更するだけで、共通レイアウトとスタイルガイド上の
  該当箇所のすべてに反映される
- **SC-004**: 共通レイアウトを適用したページが、画面幅360px・768px・1280pxのすべてで横スクロールなしに
  表示される
- **SC-005**: pushから自動テストの結果が出るまでが10分以内である
- **SC-006**: 見た目を意図的に変えた変更・代替テキストのない画像・リンク切れ・メタ情報の欠落の
  それぞれを含む変更を入れたとき、100%の割合で自動テストが失敗として検出する
- **SC-007**: 変更を含まない状態で自動テストを10回続けて実行したとき、10回とも成功する
  （テスト結果が不安定でない）
- **SC-008**: developへのpushから5分以内に、READMEの進捗表が最新の作業項目の状態を反映している
- **SC-009**: READMEだけを見て、各機能の現在の工程と残りの作業数を、1分以内に答えられる

## 現行サイトからの変更

開発原則I・IV により、共通レイアウトで現行サイトから変える点を記録する。詳細と根拠の数値は
`docs/current-site/design.md`「現行から変える点」。

| 現行の状態 | 変更内容 | 変更理由 |

| スマホメニューは jQuery で開閉するハンバーガー | `<details>` で開閉するボタン（3本線＋「メニュー」の文字） | JavaScript なしで全項目にたどり着ける（FR-012）。ボタンの意味を文字で示す（アクセシビリティ） |

## Assumptions

- 開発環境の利用者は当面リポジトリの所有者1人で、店舗関係者はREADMEとスタイルガイドページを
  閲覧する立場とする。
- 利用者の要望により、画面テストには Playwright、自動実行には GitHub Actions を使う。それ以外の
  技術選定（サイトの生成方法など）は計画（plan）で決める。
- 本機能で作るのは共通レイアウトとサンプルページまでとし、トップページ・店舗情報・商品紹介などの
  実際のページ内容は002以降の機能で作る。
- 現行サイトの調査対象は、ナビゲーション・ページ内リンク・サイトマップからたどれる公開ページとし、
  カラーミーショップ（https://waku-8.shop-pro.jp/ ）の中のページは調査対象外とする。
- 現行サイトの写真・ロゴなどの素材は和久屋が権利を持つものとして扱うが、第三者が撮影・作成したものが
  ないかは素材一覧で確認状況を管理する。
- 保存する現行サイトの画像は開発用の記録であり、新サイトには掲載しない。
- スタイルガイドページは開発時にのみ閲覧でき、本番には公開しない。
- 構造化データの店舗情報（住所・電話番号・営業時間など）は、本機能では雛形と現行サイトから
  読み取れる値までとし、正確な値の確認は店舗情報ページを作る機能で行う。
- READMEの自動更新はリポジトリのGitHub上で実行され、更新結果はdevelop（またはmain）へ直接
  コミットされる。開発者はローカルで作業を続ける前に最新の状態を取り込む。
- 自動テストで失敗した変更のマージを防ぐ設定（ブランチ保護）はGitHubの設定で行うため、
  設定手順の文書化までを本機能の範囲とし、設定作業そのものはリポジトリの所有者が行う。
