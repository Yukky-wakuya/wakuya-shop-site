# 和久屋 Webサイト Constitution

本書は、和久屋の公式Webサイト（現行サイト：https://waku-8.com/ ）を新しく作り直すプロジェクトの
開発原則を定める。仕様（spec）・計画（plan）・作業項目（tasks）・実装は、すべて本書に従う。

## Core Principles

### I. 既存サイトの踏襲

- 新サイトのページ構成・ナビゲーション・デザインの印象（ロゴ、配色、書体の雰囲気、写真の使い方）は、
  現行サイト https://waku-8.com/ をできるかぎり踏襲しなければならない（MUST）。
- 現行サイトから変更する場合は、spec に「現行の状態」「変更内容」「変更理由」を記載しなければならない
  （MUST）。認められる変更理由の例：スマートフォンで使いにくい、アクセシビリティ上の問題、
  情報が古い、技術的に再現できない。
- 現行サイトのURLは、新サイトのどのURLに対応するかを対応表にまとめなければならない（MUST）。
  URLを変える場合は、リダイレクトなどで旧URLからたどり着けるようにするべきである（SHOULD）。

理由：常連のお客様が迷わず使えること、そして店のこれまでの印象と検索順位を守るため。

### II. 静的サイト優先

- 公開するサイトは、HTML・CSS・JavaScript・画像などの静的ファイルだけで構成しなければならない
  （MUST）。本番環境で動くサーバー側のプログラムやデータベースは持たない。
- 静的サイトジェネレーターなどのビルド工程は使ってよい。ただし、使う理由と、素のHTML/CSSで
  作る場合と比べた利点を plan に記載しなければならない（MUST）。
- 問い合わせフォーム・地図・SNS連携など動的な機能が必要な場合は、外部サービスの埋め込みや
  リンクで実現する。自前でサーバー処理を作る場合は、plan の Complexity Tracking に理由を
  記載しなければならない（MUST）。

理由：費用・保守の手間・セキュリティ上のリスクを最小限にし、長く安定して運用するため。

### III. 通販はカラーミーショップに委ねる

- 商品の販売・カート・決済・在庫管理・注文者の個人情報の扱いは、カラーミーショップ
  （https://waku-8.shop-pro.jp/ ）で行う。本サイトにこれらの機能を実装してはならない（MUST NOT）。
- 本サイトから商品を購入する導線は、カラーミーショップの該当ページへのリンクにしなければならない
  （MUST）。
- 価格・在庫など変わりやすい情報は、本サイトに直接書かず、カラーミーショップ側を正とするべきである
  （SHOULD）。本サイトに書く場合は、更新漏れを防ぐ手順を plan に記載する。
- 本サイトとカラーミーショップの間を移動したとき、同じ店だと分かる見た目と導線を保つべきである
  （SHOULD）。カラーミーショップ側のデザインを調整する場合は、別の機能として spec を作成する。

理由：決済や個人情報を自前で持たず、実績のあるサービスに任せることで安全性と運用負荷を両立するため。

### IV. スマートフォン対応とアクセシビリティ

- すべてのページは、画面幅360pxのスマートフォンから一般的なPCまで、横スクロールなしで
  読めて操作できなければならない（MUST）。設計はスマートフォンを基準にする。
- 画像には内容に合った代替テキストを付け、意味に合ったHTML要素（見出し・リスト・ボタンなど）を
  使わなければならない（MUST）。
- 文字と背景のコントラスト、キーボード操作、タップしやすい大きさは、WCAG 2.2 AA を目安に
  確認しなければならない（MUST）。現行デザインの踏襲とぶつかる場合は、アクセシビリティを優先し、
  その判断を spec に記録する。

理由：お客様の多くはスマートフォンで店の情報を確認し、年齢や環境を問わず使える必要があるため。

### V. 表示速度とシンプルさ

- 画像は表示サイズに合わせて圧縮し、適切な形式で配信しなければならない（MUST）。
- JavaScriptは必要な箇所だけに使い、JavaScriptがなくても主な情報（店舗情報・営業時間・アクセス・
  商品紹介・問い合わせ先）は読めなければならない（MUST）。地図やSNSなど外部サービスの埋め込みは
  この対象外とするが、埋め込みが表示されなくても代わりの情報（住所の文字情報やリンクなど）を
  示さなければならない（MUST）。
- ライブラリや外部サービスを追加する場合は、必要な理由を plan に記載しなければならない（MUST）。
- 公開前に Lighthouse（モバイル）で Performance・Accessibility・Best Practices・SEO を測定し、
  90点未満の項目があれば、原因と対応方針を記録しなければならない（MUST）。

理由：表示の速さは来店・購入につながり、仕組みが単純なほど長く保守しやすいため。

### VI. 更新しやすい構成

- 営業時間・お知らせ・商品紹介など頻繁に変わる情報は、レイアウトのコードから分けて、
  1か所を直せば反映される構成にするべきである（SHOULD）。
- ヘッダー・フッター・ナビゲーションなど全ページ共通の部分は、1か所で管理しなければならない
  （MUST）。

理由：公開後の更新作業で修正漏れや表示崩れを起こさないため。

### VII. デザインと画面テストのコード化

- 配色・フォント・文字サイズ・余白・角丸などのデザインの値は、デザイントークン（CSS変数など）として
  1か所で定義し、各ページや部品ではそのトークンを参照しなければならない（MUST）。
  値を直接書くのは、理由をコメントで残した場合に限る。
- 画面の部品（ヘッダー、フッター、ボタン、カードなど）はコンポーネントとして作り、部品を一覧で
  確認できるスタイルガイドページを用意しなければならない（MUST）。このページは公開しない。
- 画面に関わる変更には、次の自動テストを付けなければならない（MUST）。
  - スマートフォン幅とPC幅のスクリーンショット比較（ビジュアルリグレッション）
  - アクセシビリティの自動チェック
  - リンク切れと主要な導線（カラーミーショップへのリンク、旧URLからの到達を含む）の確認
- スクリーンショットの基準画像は、OSによる描画の差が出ないよう、決まった実行環境（CIなど）で
  作成・更新しなければならない（MUST）。基準画像を更新するときは、差分を目で確認してからコミットする。
- テストは push または pull request のたびに自動で実行し、失敗している変更を main に
  マージしてはならない（MUST NOT）。

理由：見た目の変更を人の記憶ではなく記録で管理し、ページを増やしたり直したりしても
既存の画面が崩れていないことを機械的に確かめるため。

### VIII. 検索エンジンとAI検索への最適化

検索エンジン（Google・Bingなど）と、AIによる検索・回答サービス（ChatGPT・Gemini・Claude・
Perplexityなど）の両方で、和久屋の店舗と商品が正しく見つけられ、正しく紹介されることを目指す。

- 技術的な基本（MUST）
  - すべてのページに、固有の title・meta description・canonical URL・OGP を設定する。
  - 見出しは h1 から順に論理的な構造にし、1ページに h1 は1つとする。
  - 主な情報は、JavaScriptを実行しなくても読めるHTMLのテキストとして出力する（原則V）。
    画像の中の文字だけで情報を伝えない。
  - sitemap.xml と robots.txt を用意し、公開ページをすべてサイトマップに含める。
  - 現行サイトのURLからの移行で、検索評価を失わないようにする（原則I の対応表とリダイレクト）。
- 構造化データ（MUST）
  - 店舗情報を schema.org の JSON-LD（LocalBusiness 系の型）で記述する。店名・住所・電話番号・
    営業時間・地図上の位置・公式SNSやカラーミーショップへのリンク（sameAs）を含める。
  - 主な商品の紹介ページには Product などの適切な型を付ける。パンくずリストやよくある質問など、
    ページの内容に合う型があれば付ける。
  - 構造化データに書く内容は、画面に表示している内容と一致させる。
- AIに引用されやすい内容（MUST）
  - 「郡山のお土産」「日持ちは何日か」「どこで買えるか」「通販できるか」など、お客様が実際に
    尋ねそうな質問に、ページの本文で具体的かつ簡潔に答える。よくある質問ページを用意する。
  - 店名・住所・電話番号・営業時間は、本サイト・カラーミーショップ・Googleビジネスプロフィール・
    SNSで表記をそろえる。表記が異なるとAIや検索エンジンが別の店と判断するおそれがあるため。
  - 商品の特徴・原材料・由来・受賞歴などの事実は、根拠のある正確な内容だけを書く。
- クローラーの扱い
  - robots.txt では、検索エンジンとAI検索サービスのクローラーを原則として許可する（MUST）。
    特定のクローラーを拒否する場合は、理由を plan に記録する。
  - llms.txt など、AI向けの新しい仕組みは、手間が小さく害がない範囲で採用してよい（MAY）。
- 禁止事項（MUST NOT）
  - 隠しテキスト、キーワードの詰め込み、内容の薄いページの量産、事実と異なる口コミや評価の掲載など、
    検索エンジンのガイドラインに反する手法は使わない。
- 検証と運用
  - 構造化データ・メタ情報・サイトマップの内容は、原則VII の自動テストで確認する（MUST）。
  - 公開後は Google Search Console と Bing Webmaster Tools に登録し、インデックスの状況を
    確認する（SHOULD）。Bing の検索結果は一部のAI検索サービスでも使われている。

理由：お店の探し方が検索エンジンからAIへの質問にも広がっており、どちらでも正確な情報が
届くことが来店と通販での購入につながるため。

## 技術・運用上の制約

- サイトの文言は日本語を基本とする。
- 対応ブラウザは Google Chrome・Microsoft Edge・Safari（iOS / iPadOS / macOS）の、
  それぞれ最新2つのメジャーバージョンとする。原則VII の自動テストはこれらのブラウザエンジン
  （Chromium と WebKit）で実行する。
- APIキー・パスワードなどの秘密情報をリポジトリに含めてはならない。
- 外部サービス（フォーム・地図・SNS・アクセス解析など）を使う場合は、取得する情報と
  プライバシーへの影響を plan に記載し、必要に応じてサイト上で案内する。
- 写真・ロゴ・文章などの素材は、和久屋が権利を持つもの、または利用許諾を確認したものだけを使う。
- 技術スタック・ホスティング先は、本書の原則を満たす範囲で各機能の plan で決める。

## 開発ワークフローと品質ゲート

- まとまった変更（ページの追加、機能の追加、デザインの変更）は、Spec Kit の手順
  （specify → 必要に応じて clarify → plan → tasks → analyze → implement）で進める。
  文言や余白だけの小さな修正は、この手順を省略してよい。
- ブランチは「機能ブランチ → develop → main」とし、main は公開中のサイトと同じ状態に保つ。
- コミットは Spec Kit の工程ごと、実装は tasks.md のフェーズまたはユーザーストーリーごとに区切る。
  実装のコミットには tasks.md のチェック更新を含める。
- main へマージする（公開する）前に、次を確認する。
  - スマートフォンとPCでの表示
  - リンク切れ（カラーミーショップへの導線を含む）
  - 現行サイトとの対応表に沿った旧URLからの到達
  - 原則 IV・V のアクセシビリティと表示速度のチェック
  - 原則 VII の自動テストがすべて成功していること
  - 原則 VIII のメタ情報・構造化データ・サイトマップ（構造化データは Google の
    リッチリザルトテストなどでも確認する）

## Governance

- 本書は、このリポジトリのほかの手順書・慣習より優先する。
- 本書を改定する場合は `/speckit-constitution` を使い、改定内容と理由をコミットメッセージに残す。
- バージョンはセマンティックバージョニングに従う。
  - MAJOR：原則の削除、または互換性のない再定義
  - MINOR：原則・セクションの追加、または内容の大幅な拡充
  - PATCH：表現の修正・明確化など、意味を変えない変更
- 各機能の plan では Constitution Check で本書への適合を確認し、例外がある場合は
  Complexity Tracking に理由を記載する。`/speckit-analyze` でも本書との整合を確認する。
